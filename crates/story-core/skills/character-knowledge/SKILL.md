# 人物与知情核对

## 适用情景

核对人物称谓、身份变化、亲属或阵营关系，以及某人何时知道某件事；也适用于改稿前检查角色是否提前知道秘密。先列本次真正需要核对的人物和具体主张，不建立所有人物乘所有事实的清单。

## 核对方法

本局提供read_continuity(kind=knowledge)查询关键获知及澄清，read_story_resources读取本局设定/目标。记录是人物当时认知，不是世界真相；无记录保持未知。普通生成仅在原record.continuity.knowledge附少量真实变化，带本段原句；更新用已返回id，不给所有人物登记常识。

1. 普通查询先用 read_world、read_characters 查看现有人物及别名，再用 read_history 定位相关出场、揭示、告知和澄清。工具未提供的字段不要猜测，稀疏记录没有覆盖的内容仍须按需查正文。
2. 人物标识沿用现有资料；同名、相似名字或不同称呼只能先列候选，不能直接合并。身份、关系和物件持有情况按本局剧情时点核对。
3. 把“这件事是否真实”“本局是否已经发生”“某人是否获知”“某人是否相信”分别判断。亲见、明确被告知、听闻传言、推测与误信分开表达，叙述者知道不等于角色知道。
4. 每个重要知情结论尽量找到实际正文的获知、转述或澄清位置。没查到获知依据，说明尚未确认；不一概断言该人物绝对不知道。常识也不要求逐人登记证明。
5. 参考原著时读取 canon-reference，按章节范围回读原文。原著身份和未来知识不直接授予本局人物；玩家明确改变的身份、关系和经历单独保留，不用AI自己的旧错误证明玩家分支。

## 输出与完成依据

围绕指定人物给出简短结论：当前身份与称呼、关键关系、已确认获知及其依据、仍不确定或相互冲突的部分。关键事实注明本局回合或原著工具实际返回的定位，不编造人物标识或引文。

只在已读资料支持的范围内说已核对。需要改稿时，区分确定更正、合理推定及需要玩家决定的分支；不自动清洗整局人物。普通查询不写入人物、设定或剧情，不推进时间。

沉默、点头或没有反驳，只能证明出现了这种反应，不能直接证明人物相信。人物不在场或没有告知记录，只能说“尚未取得其得知的依据”，不能断言绝对不知道或仍然相信；没有明确认知证据时保持未知。

## 缺少获知依据时的答复

先给“已确认被告知/亲见的内容”和“尚未确认的内容”，再解释范围。只有缺少获知记录时，第一句应为“当前资料尚未确认某人得知某事”，不能写成“某人不知道/未获知/认知仍停留在原说法”。沉默和点头也不能进入“相信/误信”类别。

输出前检查标题、结论和逐项说明是否一致：不能正文说缺乏依据，标题却确定判为不知道。没有角色认知的直接依据，保留未确认状态；这不是否认其知情，也不替世界补写告知过程。

## 按需支持资料

需要细化核对或答复结构时，用 read_skill_resource 读取 references/method.md；examples/check.json 是独立原创示例，只用于理解方法，不能当本局事实、玩家授权或原著依据。使用读取技能时返回的固定版本与资源定位；普通调用携带 version，Agent使用本任务已读取版本，不预先加载全部附件。

## Agent执行

用 search_resources / list_resources 定位人物、卡片及相关正文，按返回 ref 用 read_resource 阅读；用 read_player_choices 核对真实玩家要求，必要时用 read_fact_sources 核对正式来源。按需 discover_tools 取得这些工具的实际参数。

默认先给只读核对结果。玩家明确要求修改时才用 stage_edit 暂存人物、关联正文和必要记录，按 world-upkeep、canon-reference 的适用规则预演并核对。不能把编辑权限当成某个关系或秘密确实成立的证据；采用情况以正式回执为准。
