## 已采纳

### D101 v3 体验优先重构，v2 计划归档

- 状态：已采纳（2026-10-16）。
- 决策：用户明确指出 v2 成果“看似功能完善，实际难以代入、操作不便、很多功能不好用”，要求重头重构。v3 的目标顺序为：① 学习同类产品，体验上向成熟产品看齐；② 结合穿越题材做出特色；③ 让玩家舒适好用；④ 改善 UI 与前端（后置）。优先手机 App，电脑端只需能跑。[第三版计划](PLAN_V3.md)成为当前唯一的产品与工程计划；第二版计划、旧台账、验证记录移入 `docs/archive/v2/`。
- 理由：v2 的验收以“不出错、可审计”为中心，没有“好不好玩”的门槛；结果是事务、校验、恢复做得很重，玩家能接触到的游戏层很薄。
- 代价：v2 的大部分游戏层代码不再使用；需要重新实现回合、记忆、分支等功能。
- 重评条件：用户改变目标顺序或平台优先级时。
- 关联任务：R00-T001～R00-T004。

### D103 技术栈：保留 Tauri 2 + React/TS，游戏引擎改用 TypeScript，Rust 收缩为平台服务

- 状态：已采纳（2026-10-16）。替代 v2 D006（独立 Rust 核心）和 D005 中“业务逻辑在 Rust”的部分。
- 决策：
  - 继续使用 Tauri 2 作为 Android/Windows 外壳，React + TypeScript + Vite 写界面。
  - 游戏引擎（回合流程、提示词组装、输出解析、状态记账、记忆、分支）写成**不依赖界面和平台的 TypeScript 模块**。
  - Rust 只保留四类平台服务：① 存储（SQLite，按粗粒度命令做事务）；② 密钥；③ 模型请求的流式传输（Rust 注入 Key，JS 永远拿不到明文）；④ 文件导入导出。
  - 引擎通过一个 `Platform` 接口访问这些服务；另实现一个“浏览器开发适配器”，用于在电脑浏览器里直接游玩调试（见 D108）。
  - 因为 Android 在后台会暂停 WebView 中的 JS，Rust 端在生成时把累计文字写入私有临时文件，界面回到前台或重启后通过 `resume` 补齐；Key 绑定到服务地址前缀，请求地址不匹配时拒绝。
  - v2 `stream.rs` 只复用 HTTP 客户端、有界读取、超时、取消和回显过滤；删除其 delta 字段白名单与载荷校验，改为原样转发 `data:` 行，由 TypeScript 统一解析。
- 理由：
  - 游戏层现在主要是“和大模型打交道”：提示词和解析需要频繁试错，用 TypeScript 改动快、测试快，前后端不用来回同步类型。
  - 浏览器开发台和后续网页版可以直接复用同一引擎。
  - v2 已验证的 Rust 平台代码（Keystore、DPAPI、SSE 流式与取消、文档选择器、TLS、窗口边距）可以直接复用。
- 代价：需要重写游戏层；放弃 Rust 端的强类型协议校验，改由 TypeScript 测试保证。
- 重评条件：TypeScript 引擎在手机上出现明显性能问题（如长局卡顿），或 Tauri Android 出现无法绕过的 WebView 限制。
- 关联任务：R01-T001～R01-T003。

### D104 叙事优先的回合输出与宽容的状态记账

- 状态：已采纳（2026-10-16）；具体格式由 V101 实验决定。替代 v2 D003 的严格解读、D008 的“全有或全无”提交和 TURN_V1 协议。
- 决策：
  - 模型每回合先写**正文**（纯文本，可流式逐字显示），正文之后附一个**简短的记录块**（选项 + 少量状态变化）。正文永远不放在 JSON 字段里。
  - 状态变化使用小词表：时间流逝、地点、钱、物品增减、人物（新出现/更新态度）、伤病与状态、目标与线索、大事记。
  - 程序**逐条**校验和应用状态变化：合法的应用，不合法的丢弃并在开发者模式里记录；**不因为某一条不合法而拒绝整个回合**。
  - 记录块缺失或损坏时，正文照常显示，**在下一回合开始前**同步发起一次“补记”调用从正文提取（期间输入栏显示“整理中…”，超时 20 秒）；补记也失败时，本回合记为“无记录”，状态不变，提示玩家可在面板手动修正。补记绝不事后改写已有子节点的快照。开场的记录必须成功才能进入第一回合。
  - 硬规则由程序裁决（见 D113），例如钱不能为负、已死亡的人不能复活；冲突时以程序状态为准，并在下一回合提示模型。
- 理由：v2 真实评测 36 次生成中 6 次因 JSON 格式被整回合拒绝，每次失败都要玩家手动重试；模型同时写小说和填 9 类操作表，叙事质量和速度都受影响。成熟产品（AI Dungeon、SillyTavern 状态栏、《崇祯》）都是“叙事为主，状态另记”。
- 代价：状态记录可能偶尔遗漏或不准，需要“补记”和“手动修正”兜底；正文与状态的一致性要靠提示词和评测持续改进。
- 重评条件：V101 实验显示某种格式在目标模型上成功率低于 95%，或状态遗漏让玩家明显感到“失忆”。
- 关联任务：R01-T004、R02-T003、R02-T004、R02-T005。

### D105 回合树与每节点状态快照

- 状态：已采纳（2026-10-16）。简化替代 v2 D007、D013、D034、D037。
- 决策：
  - 每个世界的所有回合组成一棵树：每个回合有一个父回合。
  - **世界线**是随游玩前移的指针（类似 git 分支），**书签**是固定指针。“重说”= 同一父节点下的兄弟节点，用 ‹ › 切换；“撤销/重做”= 指针沿父节点 / `last_child_id` 移动；“回到这里”“改我的行动”= 从旧节点开出新世界线，原线不动；离开的路线在分叉后不少于 3 回合才自动登记，避免列表刷满。
  - 每个回合节点保存一份完整的状态快照（JSON，单独存 `states` 表），回到任意节点即可得到当时的完整世界。
  - 组装上下文时只沿“当前节点 → 根”的路径取内容，天然不会混入其他分支的信息。
  - 面板中对数值、物品、人物、目标的手动修改生成隐藏的“修改节点”（补丁）；重说其前一回合时自动沿用该修改。
  - 要点、叙事方针、文风篇幅属于世界级内容，跨世界线保留，不放在快照里（见 D106）。
- 理由：撤销、重说、编辑、分支、回溯在 v2 中是多套机制，v3 统一成树操作，实现简单，分支隔离自然成立。
- 代价：快照有冗余；预计每回合几 KB 到几十 KB，1000 回合在几十 MB 以内，可接受。规模过大时再做差量压缩。
- 重评条件：单个世界存档超过 200 MB 或读取明显变慢。
- 关联任务：R02-T002、R06-T001。

### D106 记忆体系：故事卡、要点、章节摘要、叙事方针

- 状态：已采纳（2026-10-16）。替代 v2 D012、D031、D035 的角色认知引擎与多 sidecar 方案。故事卡的种类、常驻规则和“不设置顶”由 D121 细化（2026-10-17）。
- 决策：
  - **故事卡**：人物、地点、势力、物品、设定各一张卡，有名字、别名（触发词）、正文描述。新人物或地点出现时自动建卡，玩家可编辑、可置顶。正文或最近对话出现触发词时，把卡片内容放进上下文。
  - **要点**：玩家标记的“必须记住”的事，常驻上下文。要点属于世界级内容：手动新建的是全局要点；从某段正文“记住这件事”生成的要点带来源回合，只在来源回合位于当前路径上时生效，避免把一条世界线发生的事带进另一条。
  - **章节摘要**：每 12 回合（可调）后台自动把旧剧情压缩成一段摘要；原文永远保留，摘要可重写；只在其最后一个回合位于当前路径上时使用。
  - **叙事方针**（类似 AI Dungeon 的 Author's Note）：放在上下文靠后位置，影响文风和节奏。
  - 暂不做 v2 的“每个角色知道什么”逐条认知引擎；需要时在人物卡里写“他知道/不知道……”。
- 理由：这是 AI Dungeon、NovelAI、SillyTavern 等产品验证过的成熟结构，玩家容易理解和编辑；v2 的认知引擎复杂且对体验贡献有限。
- 代价：秘密和信息差靠提示词维持，偶尔会“泄密”。
- 重评条件：长局评测中“泄密”或“失忆”成为主要投诉。
- 关联任务：R04-T001～R04-T005。

### D107 调用策略

- 状态：已采纳（2026-10-16）。替代 v2 D009、D023、D040 的严格调用预算与“固定一次尝试”。
- 决策：
  - 每个玩家回合只有一次**主叙事调用**，必须流式返回。
  - 允许后台**辅助调用**：章节摘要、补记、故事卡整理。可单独配置一个更便宜的“辅助模型”，默认与主模型相同。
  - 网络或服务错误发生在**出第一个数据（推理或正文）之前**时，自动重试 1 次；出字后中断则保留已写部分，提示“续写/重说”。服务明确拒绝（内容安全）时不重试。
  - 推理内容也计入“有数据”，参与超时计时，避免推理模型被首字超时误杀。
  - 记录每次调用的用量（token、耗时、估算费用），在“设置 → 用量”查看，不在游玩界面打扰玩家。
- 理由：v2 的“每次都不自动重试、每次都提醒可能计费”让玩家很累；成熟产品都会静默处理偶发网络错误。
- 代价：极少数情况下多一次计费调用。
- 重评条件：用户反馈费用不可控时，增加每日/每世界预算上限。
- 关联任务：R01-T003、R02-T005、R04-T003。

### D108 开发回路：浏览器手机尺寸开发台 + 阶段性真机

- 状态：已采纳（2026-10-16）。
- 决策：
  - 同一套引擎和界面可以在电脑浏览器里以手机尺寸（如 393×852）直接游玩：存储用浏览器本地数据库，模型请求经 Vite 开发代理转发，Key 放在本地不入 Git 的 `.env.local`。这个模式只用于开发，不对外发布。
  - 每个阶段结束、以及关键交互完成时，打包 APK 到手机上验收。
  - 优先尝试 `tauri android dev` 无线热更新；小米手机 ADB 安装受限（v2 时出现 `INSTALL_FAILED_USER_RESTRICTED`），需开启开发者选项中的“USB 安装”“USB 调试（安全设置）”，不行则继续用“放到下载目录手动安装”的方式。
- 理由：v2 时期每次改动都要手动装 APK，手机体验迭代极慢；浏览器手机尺寸能覆盖大部分交互调试。
- 代价：浏览器和 Android WebView 存在差异（输入法、返回键、后台、字体），这些必须在真机验收。
- 重评条件：真机与浏览器表现差异频繁导致返工时，提高真机验收频率。
- 关联任务：R01-T002、R01-T005。

### D109 每阶段以用户试玩体验为门槛

- 状态：已采纳（2026-10-16）。
- 决策：每个阶段（R02 起）的完成条件同时包括：① 工程检查（单元测试、构建）；② 脚本化模型评测（固定剧本跑若干回合，统计成功率、延迟、一致性）；③ **用户在手机上试玩并填写简短问卷**（流畅、代入、好操作、记得住、想继续玩，各 1～5 分，加自由意见）。问卷平均分低于 4 或用户明确不满意时，阶段不算完成。
- 理由：v2 以“工程上没错”为完成标准，结果做出了不好玩的产品。
- 代价：每阶段需要用户投入 20～40 分钟试玩。
- 重评条件：用户希望减少参与频率时，改为每两个阶段一次。
- 关联任务：各阶段最后一个任务。

### D110 新应用 ID，与旧版共存，旧存档不迁移

- 状态：已采纳（2026-10-16，用户回复“开始吧”接受默认值）。
- 决策：v3 使用新的 Android 应用 ID（暂定 `io.timejump.chuanyue`）与新的应用名，手机上可与旧版 “Lishi Probe” 共存。v2 世界存档都是测试数据，不做迁移；旧版可随时从 `legacy-v2-final` 标签重新构建。
- 理由：新存档结构与 v2 完全不同，迁移成本高、收益低；共存方便对比新旧体验。
- 代价：手机上暂时有两个图标；旧档剧情不能带入新版。
- 重评条件：用户希望保留某个旧世界时，可单独做一次性导入（只导入剧情原文和主角信息）。
- 关联任务：R01-T001。

### D111 历史真实感以“时代包”为主，联网考据后置为可选

- 状态：部分替代（2026-10-17，D121）：时代资料改由玩家在设定集里定义或让 AI 整理，时代包降为可选的内置卡组；“联网考据后置为可选”仍然有效。原文如下。替代 v2 D015、D016、D038 的研究与证据冻结机制。
- 决策：
  - 为常玩时代准备**时代包**：纪年方式（年号、干支、月日、时辰）、货币与物价锚点、称谓、度量、日常生活细节、社会阶层、关键历史事件时间表、文风提示、常见时代错误清单。时代包由 AI 起草、人工抽查，标注来源和可信度。

### D113 数值框架：少量核心数值由程序裁决，叙事必须服从

- 决策：

  - 这些数值存放在状态快照里，由程序计算和约束；每回合把当前数值告诉模型，模型在记录块里提出变化，程序决定最终结果。

- 重评条件：试玩中玩家觉得数值无感或负担过重。

### D116 生成期间使用 Android 前台服务保持联网

### D117 开局以“作者模式”为中心

- 状态：已采纳（2026-10-16，用户试玩第一版后的反馈）。修订计划第 4.1、4.2 节与 R03-T004 的开局向导设计。

- 决策：
  - 开局只有一张可自由编辑的“开局设定”：故事设定（相当于开局提示词，会一直放进上下文）、主角（名字、年龄、性别、身份与处境，均为自由文字）、穿越方式（魂穿 / 身穿 / 投胎 / 不穿越）、开场（AI 来写，可给提示；或玩家亲手写第一段，AI 只做状态整理）。另有可选的要点、给 AI 的额外规则、叙述视角（你 / 我 / 他）、文风、篇幅、选项数、内容尺度、时代资料。
  - “一句话想法 + AI 帮我补全”：只补空着的字段，不改玩家已写的内容。
  - 模板只是“灵感”：点一下填入全部字段，玩家随意修改；模板覆盖各阶层（皇子、相府庶女、锦衣卫、行首、盐商独女、粟特商人、流民、身穿现代人等）和多个朝代；玩家可把自己的开局存为“我的开局”。“随便穿”= 随机模板直接开始。
  - 性别规则：身份本身隐含性别（公主、宫女、皇子等）时模板固定性别，界面显示“由身份决定”，不再让玩家选；中性身份的描述不含性别词，才让玩家选；玩家可手动解除锁定。提示词要求“主角的性别、身份以【当前】为准”。
  - 游玩中新增“写”模式：玩家以作者身份写的文字直接成为剧情，AI 视为已发生并接着写。故事设定、要点、额外规则、叙事方针在游戏中随时可改。
  - 时代资料（时代包）改为可选：不选时，时代以故事设定为准；开场记录给出日期、时刻、货币单位和主角初始钱数（按身份而定）。
- 理由：AI Dungeon 自定义开局、NovelAI 空白稿纸、酒馆“世界书 + 开场白”都说明，玩家最看重的是“自己定故事、AI 来写”；固定身份签与统一初始钱数让所有开局都像一个剧本。
- 代价：自由文字开局对提示词要求更高，模型可能偏离玩家设定；没有时代包时，货币与时代细节依赖模型。
- 重评条件：试玩中发现 AI 经常不遵守故事设定，或玩家觉得开局表单太长。
- 关联任务：R02-T012、R02-T008、R02-T013、R03-T004。

### D119 游戏日期由程序按简化农历推算

- 状态：已采纳（2026-10-17）。落实计划第 4.6 节“程序累计并换算日期；模型不直接写日期”。
- 决策：
  - 开场记录给出结构化的开局日期（年号、年、月、日，尽量附公元年）；之后的日期只由程序用“开局日期 + 经过的时间”推算，模型不再写日期。
  - 中国背景用**简化农历**：每年 12 个月，单月 30 天、双月 29 天，不设闰月，正月初一过年。西方背景用公历月长（不计闰年）。
  - 年号在过年时按时代包的年号表切换（如天宝十四载之后是至德元载）；时代包没有年号表或开局年号不在表中时，年号一直往下数。公元前没有 0 年。
  - 主角按虚岁在过年时长一岁。
  - 不接入农历库。评估过 lunar-javascript（MIT，无依赖，约 0.5 MB）：未写明支持的年份范围，1582 年以前按儒略历换算，古代年份的月份与当时实际历法也有出入，不足以支撑“考据级”，却会显著增加体积。
- 理由：玩家感受到的是“天宝七载冬月十七，酉时”这样的纪年与月日，不会去核对朔日；程序推算保证日期只前进、和经过时间一致，不受模型笔误影响。
- 代价：月份大小与真实历法不完全一致（一年 354 天）；节气只能按月份近似。
- 重评条件：玩家在意具体某天的真实朔望或节气，或需要与真实历史日期逐日对照。
- 关联任务：R03-T003。

### D120 时代包格式：TS 数据模块，身份签兼作开局模板，摘录限 1000 字

- 状态：部分替代（2026-10-17，D121）：时代包改称“内置卡组”，开局时转成本局的时代卡和地点卡；按月生成的摘录改为一张静态的时代卡。TS 数据模块、身份签兼作模板、时代错误的字段、1000 字上限仍然有效。字段说明见 [时代包写作指南](contracts/ERA_PACK.md)。
- 决策：
  - 时代包是 `src/content/eras/` 下的 TypeScript 模块，只含普通数据（可原样导出为 JSON），由 `src/engine/era/validate.ts` 校验；计划第 7 节写的“时代包数据（JSON）”按此执行。好处是类型检查和编辑器提示，不需要额外的加载与解析代码。
  - 时代包的身份签就是开局模板：模板列表由各时代包的身份签加上没有时代包的手写模板组成，不再分别维护两份。
  - 时代错误分三部分：`name`（叙事者看到的“不要出现”）、`note`（为什么，给玩家和以后的时代错误提示）、`instead`（用什么代替，叙事者看到）；`match` 是评测统计用的字面词。

- 重评条件：需要让玩家导入或编辑时代包时，再加 JSON 导入；上下文预算紧张时，再考虑按场景挑选禁忌。
- 关联任务：R03-T001、R03-T002、R03-T004。

### D122 游玩中由 AI 定期整理设定集，结果是可撤销的 AI 修改

- 状态：已采纳（2026-10-17）。细化 D106、D121 中“R04 起 AI 在游玩中提议新卡”。
- 决策：
  - 同一路线上每过 6 回合，后台用辅助模型读这几回合的剧情：给有名字、以后很可能再出现的势力、物品、设定建卡（一次至多 3 张），给没有描述的地点补一句描述，更新 AI 自己以前写的卡；人物不建卡（人物表每回合由记账维护）。
  - 只动 AI 写的东西：玩家写的卡片、内置卡组的卡片和有描述的地点一律不改；玩家删掉过的名字记下来，以后不再建。
  - 结果作为一个“AI 整理了设定集：……”的修改节点挂在当时最新的回合之后，可以撤销；如果整理期间玩家已经回到那几回合之前，结果作废。重说某一回合时，AI 的整理不随之沿用，下一回合会按新的文字重新整理。
  - 回合与修改按世界排队写入，整理结果不会和正在写的回合交叉；本局设置里可以关掉。
  - 同时，人物表在提示词里按“在场优先”排列：最近三回合或本次行动提到的人带上备注，其余人只给身份和态度，超过 30 人只列名字。
- 理由：成熟产品的资料库（AI Dungeon 的故事卡、NovelAI 的 Lorebook）靠玩家手动维护，长局里很少有人坚持；让 AI 定期补记、玩家随时改和删，既省事又不丢掌控。只在固定间隔整理，比每回合都让主模型多写卡片更省 token，也不影响记录块的解析率。
- 代价：每 6 回合多一次辅助调用（输入约 3k～5k token）；AI 建的卡可能不准，需要评测和玩家修改；整理落后于剧情最多 6 回合。
- 重评条件：评测显示建卡重复、编造或漏记严重；玩家觉得故事里的“AI 整理了设定集”提示太吵；或费用不可接受。
- 关联任务：R04-T001、R04-T005。

## 待验证

### V101 回合输出格式实验

- 状态：待验证。
- 问题：哪种格式能在目标模型上同时做到“正文流畅流式、记录块稳定可解析、延迟低”？
- 候选：A. 正文 + 末尾标签包裹的紧凑 JSON 记录块；B. 正文 + 末尾逐行文本记录（如 `钱 -2 文`、`得 胡饼 1`）；C. 只写正文，另发一次辅助调用提取记录。
- 验证方案：同一组 20 回合固定剧本，在用户的模型上各跑一遍（有条件时再加一个国产模型），统计记录块成功率、首字延迟、总耗时、token、状态准确度和人工评价的正文质量。
- 通过标准：选出成功率 ≥ 95%、首字延迟不劣于纯正文、正文质量不下降的格式。
- 结论（2026-10-16）：选定 **A（正文 + `<record>` JSON）**。三种格式记录均 20/20 可解析；A 探针 10/12 最高、首字中位 6.8 秒、每回合中位 12.1 秒；C 每回合慢约 7 秒、多 30% token。见 [R01_FORMAT](validation/R01_FORMAT.md)。
- 关联任务：R01-T004。
