## 2. 稳定身份、名称与别名

### 2.1 ID 与名称规则

- 实体 ID 沿用 v1：1～64 字节 ASCII 字母、数字、`-`、`_`，大小写敏感。世界 ID 与实体 ID 分开；对象的身份键为 `(worldId, entityId)`，后续分支改变状态，不改变同一实体的身份。
- 已存在实体的 ID、kind 永不可改，ID 不回收。改名、身份揭露、关系改变、死亡都继续引用同一 ID。死亡不能通过更换姓名复活；删除与合并实体不在本任务范围。
- 同名不同 ID 合法。自动处理行动时，名字匹配到两个人不得按列表首项或关系强度偷偷选择；使用当前场景/已知身份进一步缩小，仍有歧义则给出可区分候选。候选文案可以显示“王安（药肆掌柜）”和“王安（货栈伙计）”。
- 匹配第一版只执行首尾空白去除及精确字符串比较；不修改中文原名，不把繁简字、拼音、谐音或称谓自动合并。索引可增加归一化键，但必须保留原文并记录索引版本，身份不能由归一化文本推定。

### 2.2 建议名称记录

实体保留 `name` 作为当前正式名称，增加 `aliases`。每条别名包含 `text`、`kind`、`sourceEventId`；kind 为 `former_name`、`nickname`、`title`、`transliteration`、`other`。初始或旧存档来源可空，新回合别名必须引用本回合已验证事件。实体名维持 v1 的 256 字节边界；每实体最多 32 条别名，每条最多 256 字节。同一实体同一 text 不重复存储，当前正式名称不另占别名项。

`rename_entity` 必须提供 `entityId`、`expectedName`、`newName`、`eventId`。旧名自动加入 `former_name`，新名改为正式名称；若新名原来也是别名，合并该记录。`add_alias` 只增加称呼，不创建人、不改变 alive，也不授予任何角色新知识。新名与旧名相同视为无效操作，避免制造伪变化。

别名来源事件参与人物知情过滤。一个秘密身份的正式名称不能因为数据库里有它就进入所有 NPC 对话；具体玩家/角色显示名由知识视图选择，必要时使用已知称呼和身份描述。初始名称以及 v1 已显示名称的历史可见性记录为“旧版本未细分”，不倒推为所有 NPC 都知道。

## 3. 实际持有物：数量、保管与位置

### 3.1 建议规范化记录

保留 `kind=item` 的实体身份，增加 `itemHoldings`：

```text
itemId
status: known | legacy_unknown
holderId: person/organization ID 或 null
placeId: place ID 或 null
quantity: 非负安全整数或 null
unit: 非空字符串或 null
source: 核心生成的来源引用
```

首期明确记录“实际持有/保管”，不推断法律所有权。容器嵌套、重量、容量、装备栏、同时多人持有一件物品、复杂产权均后置。`known` 时 quantity/unit 必填；quantity > 0 时 holderId 与 placeId 必须恰好有一个，表示有人保管或物品留在某地。quantity = 0 时两者均为 null，表示已消耗或当前不可用；原物品实体仍保留，旧回合仍能引用。`legacy_unknown` 时这些字段全为 null，只在独立旧属性展示中保留未经验证的原始值。

每个 itemId 最多一条持有记录。两份同类物品可是一堆 quantity=2；两个独立钥匙拥有不同 ID，名称可以相同。增加或扣除同一堆不得换单位；拆分成新堆需要新 ID 和有守恒检查的明确操作，本任务先不提供自动拆分。初始行囊以可信初始设置建立player/1/件；旧存档仅在初始结构匹配且完整历史中持有属性未变化时沿用该特例，转交后不得重新归给player。新物品须在同回合建立规范化持有记录。数量归零后保持已耗尽记录，本期重新购得同类物品使用新ID及显式新持有记录，不对空持有记录直接补货。

### 3.2 操作与预条件

建议只增加以下闭集操作，避免 `set_attribute` 旁路：

| 操作 | 必填内容与确定性规则 |
| --- | --- |
| `set_item_holding` | itemId、expectedHolding（显式null或完整status/holderId/placeId/quantity/unit）、holderId、placeId、quantity、unit、eventId；null仅允许尚无持有记录的新item，非null必须逐字段匹配旧记录。用于首次建立、转交或确认异常旧记录；普通转交保持数量与单位 |
| `change_item_quantity` | itemId、expectedHolding（完整五字段）、delta、eventId；known旧记录逐字段匹配，保管人/地点/单位不可悄悄改变；不能负数或溢出；归零自动清 holder/place，实体保留 |

`set_item_holding` 不是可以由资料页或世界外指令任意写事实的接口，只能属于正式回合输出。对不满足固定迁移规则的旧属性，首次确认必须在新剧情中明确发生查验/确认事件。合法旧记录可确定性转换为带legacy来源的库存，代表兼容保留原游戏记录，不把历史考证程度升级。

迁移后 `ownerId`、`holderId`、`quantity`、`unit` 及其大小写变体成为 item 的保留属性键；旧值可读，`set_attribute` 不能再改它们。正式面板与结算只读取规范化记录，异常旧字符串标注为“旧版记录，待确认”；合法转换记录显示“旧版记录，经格式校验”，防止两套数量互相冲突。

购买需同时验证现金操作和物品操作。付款成功但末尾物品引用非法时整回合回滚，既不扣钱也不加物品。只获得知情事件不意味着获得钥匙；资源是现有非负数值系统，本任务不使用负 cash 伪造债务。

## 4. 持续状态与来源

沿用 condition ID 和主体，增加 `category`、`startedSource`、`lastChangedSource`、`resolvedSource`；category 初期为 `injury`、`illness`、`obligation`、`other`、`legacy_unspecified`。仅描述性伤病、债务或承诺，不引入诊断、利息或自动疗程引擎。

- 新增状态必须 active=true，引用既有实体与新事件。description 仍为最多 2048 字节的可显示文本。
- `update_condition` 提供 conditionId、expectedDescription、newDescription、eventId；只能更新仍活跃的同一状态，保留最初来源。用于扭伤好转、承诺条件变化等，不增加重复“同一扭伤” ID 来规避持续事实。
- `resolve_condition` 在 v2 增加 eventId，已有活跃状态才可解决，写入 resolvedSource。已解决记录保留；不能再次解决或悄悄变 active=true。复发可建立新 ID，并通过事件说明关联旧伤。
- 时间推进、休息、摘要、固定提醒不能自行解决状态。核心只能验证明确操作/引用和预条件；“两小时足以治愈”的医学或情节判断仍须评测和人工检查，不因 JSON 合法就称合理。
- 人物死亡不删除其状态、关系、资源与物品记录，也不自动把遗物归给玩家。遗物转交是后续正式回合。

来源采用核心生成的 `StateSource`，最少为 `initial`、`turn` 或 `legacy_snapshot`。turn 来源带正式 operation/turn ID 和 event ID；legacy_snapshot 带源回合 ID（初始为空）及原格式版本。模型只提供 eventId，不能伪造提交 ID、写入时间或备份路径。所有操作首先验证到候选状态，来源在事务提交身份确定时写入；失败不留下新的正式来源。

来源不只适用于伤病和物品：v2 实体需 createdSource/nameSource/lifeSource，属性另有按现有属性键对应的 attributeSources；资源与关系需 lastChangedSource，时间与主角地点需 lastChangedSource，事件需 createdSource。这些字段只记录已有规范化值的来源，不再复制一套金额、生命状态或文本事实；校验器核对来源存在、引用节点可见及事件关联主体。纯状态应用接口需显式传入可信 CommitContext（当前 operation ID、基准节点），再由核心生成来源；模型不能在输出中填写 CommitContext。未来查询投影可重建来源索引，不能反向改写快照。

旧状态的始发来源可由顺序扫描不可变快照找到第一次出现及 active→false 的回合，记录为 legacy_snapshot；描述没有明确原因时保持 `legacy_unspecified`，不得借迁移再调用模型猜原因。

## 5. 客观事实、事件、主张与人物已知

### 5.1 三类权威内容

1. **当前世界事实**：规范化快照的 alive、资源、持有物、关系、持续状态及地点。来源指回初始设置或正式回合。它们不是摘要或模型评语。
2. **已经发生的事件**：继续使用稳定事件 ID。增加 disclosure：`public`、`restricted`、`legacy_unspecified`；旧 description/entityIds 保留。事件不可修改；信息“公开”只代表允许披露，并不自动使所有 NPC 知情。
3. **人物提出或听到的主张**：新增 `claims`，最少含 id、text、entityIds、assessment（unverified/supported/refuted）、evidenceEventIds、createdSource。主张不同于客观事实；声称某人死了不会执行 `set_life_status`。更新 assessment 必须通过明确 `assess_claim` 操作引用新的正式证据，保留旧回合中当时的判断。

本任务的来源只指游戏事件与回合；外部文献、研究来源、网页证据由 M05 建立，不能让模型自行写 URL 就获得已核实来源身份。复杂判断 supported/refuted 仍是游戏中采用的判断，不升级为真实历史考证。

### 5.2 知识记录

v2 的 `knowledge` 建议为：

```text
actorId: person ID
targetType: event | claim
targetId
certainty: certain | reported | doubtful | legacy_unspecified
acquisitionMode: observed | told | inferred | legacy_unspecified
acquisitionEventId: 已发生事件 ID 或 null
source: 核心生成的正式来源
```

唯一键为 `(actorId, targetType, targetId)`；首次登记用 `record_knowledge`，后来改变确信程度用 `update_knowledge` 并检查原 certainty。不能凭空引用别人的未提交草稿或不存在的事件/主张；新增记录需 acquisitionEventId，legacy_unspecified 仅供旧格式转换。

新增数组边界建议：每实体 aliases≤32；itemHoldings≤现有item实体数且总数≤512；claims≤4096；knowledge≤4096；单 claim text≤2048字节、实体/证据引用各≤64。现行每回合128操作、32新事件、256KiB输出及JS安全整数边界保持；原4096 knownFacts上限迁移对应knowledge，不无限扩张。所有新普通文本延续UTF-8字节、非空及控制字符检查，未知枚举和字段拒绝。规模调整另按300回合实际测量决定，不因这里列出上限就声称上下文能容纳这些内容。

角色确信一个 claim 不证明 claim 为真，claim 被证伪也不自动让曾经听信的所有人物改观点。更新知情和世界事实是两种独立操作。同一人物可以“确信传闻”，而客观 alive 仍为 true。

不为全世界所有人建立思想档案。维护主角、在场人物和影响活跃事件的人员；没有记录表示程序没有证明其知情，不表示其一定失忆或已经知道。新建 NPC 不自动继承玩家或所有 NPC 的 knownFacts。

### 5.3 查询与上下文接口

建议核心提供只读函数：`entity_by_id`、`resolve_visible_name`、`held_items`、`active_conditions`、`knowledge_for_actor`、`source_for_fact`。查询都接收世界/当前正式节点；M04 再实现祖先路径过滤，不提前以全库宽查询替代分支隔离。

人物对话视图只得到其已知事件/主张与当前可观察事实。推演叙事者可以读取受限世界事实，但必须显式区分“叙事者用于计算的隐藏信息”与“角色可说出的信息”。玩家调试页与普通人物页不能共用未经筛选的 DTO。单个模型同时扮演叙事者和角色时，提示与评测必须检查秘密泄漏；仅有数据库知识字段不证明模型遵守。

### 5.4 角色最近已知值与主张视图

`knowledge_for_actor`禁止直接返回全局claim对象。角色DTO只含其已知文本、自己的certainty/acquisitionMode和已知证据ID；后续全局assessment变化或新证据，只有明确record/update_knowledge后才能进入该角色视图。叙事者全局判断保留在独立受限视图，不覆盖角色belief。

实体的最新name/life/attributes来源不是人物认知历史。`actor_fact_view`须按该角色当时可见的正式历史返回最近已知值及对应来源：秘密改名或死亡后仍保留角色之前知道的名字/存活认知；没有可见历史时返回unknown。明确当前可观察信息可更新视图，但由受控观察规则或正式获知事件授权，不因为属性在当前快照里就可见。别名召回也按此过滤。为此查询输入包括正式历史的可见来源索引，不能只过滤最新字段。

生产接线必须替换当前`compile_game_prompt`的整份WorldState直接序列化。新模型输入分开推演所需硬事实、角色已知视图与禁止泄漏约定；普通UI也只接收玩家可见DTO。确定性视图测试先证明隔离，真实模型遵守另行评测，不能以提示词保证绝不泄漏。

## 6. 版本与严格解码

建议正式输出与规范化状态升级至 **protocolVersion=2**。理由是现有 v1 禁止未知字段、名称修改和新操作，前端也只接受 version=1；在 version=1 下默默增加别名、持有物、知识参数会改变旧语义并破坏严格解码。提示版本独立升级，不能用 prompt 版本代替存档协议版本。

输出 DTO 与正式状态 DTO 需要分开：模型的 create_entity/event/claim 输入不允许包含核心来源字段，由可信 CommitContext补齐；不能因为存储结构必填 createdSource就要求模型自己编造来源。所有改变事实的 v2 操作统一必填 eventId（知识获知事件可同时作为 eventId），继承的资源、关系、属性、生命状态和移动操作也增加该字段。timeAdvance增加显式可空eventId；推进量大于0时必须引用本回合事件，0时可null。新事件先登记、操作依次应用、最终统一检查来源与主体引用，延续v1原子规则。

建议三层版本分别维护：

| 版本 | 建议值/用途 |
| --- | --- |
| 模型输出/规范化状态 | v2，新的对象及闭集操作；继续保持必填字段、显式 null 和 unknown field 拒绝 |
| SQLite `user_version` | v2，登记升级备份与格式政策；仍是每世界一个库、同一短事务提交 |
| 旧状态转换器 | `legacy_adapter_v1`，确定性、无模型调用；保留固定测试防止以后更新改变旧事实 |

保留只读的 v1 DTO、解析/校验器，新增按 protocolVersion 分派的 `StoredState`/`StoredOutput`。不能把所有结构改成默认空值再宽松解析。未知将来版本明确拒绝，不能猜降级。

旧回合读取时可以返回原始版本及转换后的展示视图；新正式回合只产生 v2。过渡版本的 UI 必须明确读取混合历史，不能让旧 GameClient 对 v2 误报损坏。旧 v1 模型输出默认不接受为升级世界的新回合；如需临时兼容路线，须另记决策，不能静默回退。

## 7. SQLite v1 → v2：先备份，再最小迁移

### 7.1 不改写旧正式历史

真实表名为 `game_world`、`game_operations`、`game_turns`。v1 没有独立 `state_snapshots` 表；快照在 `game_turns.state`，原始输出在 `game_turns.output`，初始与当前状态在 `game_world.initial_state/current_state`。实施时不要按计划中的概念表名假设它们已经存在。

建议原 `game_turns` 行、output/state/narrative/choices、操作输入与初始世界字段保持字节不变；不删除不可变触发器来批量改写。新旧回合的版本从 JSON 明确读取。`game_world.current_state` 作为 head 的当前投影可更新为规范化 v2，但 head、turn_count 不变，不伪造一个世界内回合；它必须等于对应旧 head 快照及完整历史来源索引经固定转换器所得的状态。head 为空时从 initial_state 转换。后续提交继续原子更新正式回合、当前投影和操作终态。

数据库 v2 初期只需增加 `game_migrations`（from/to、adapterVersion、backupBasename、backupSha256、completedAtMs）等升级记录，不必为所有概念提前创建一套可独立改写的实体表。正式查询先基于规范化快照；检索投影在 M03-T002增加且可重建。迁移记录不包含 API 配置、Key、真实绝对私有路径或原始诊断正文。

### 7.2 安全流程

迁移只由选定世界的显式受控入口触发。`list_game_worlds`当前逐个调用GameStore::open，不能把自动迁移放入open使查看列表升级所有世界。版本/摘要只读探测不得写入；打开旧世界应返回升级需求，在备份与兼容验收完成后才启用入口。这里的显式操作是产品行为，无需开发过程中反复要求用户批准固定夹具迁移。

1. 取得现有世界 `.owner-lock`，核对 application_id、user_version、当前 head 与状态一致性；已有活动操作必须先进入现行启动恢复的 interrupted 终态，不能迁移后自动重发。
2. 使用 SQLite 一致性备份接口生成私有目录中的独立备份，包含已提交 WAL 内容；不在数据库仍运行时直接复制主 `.sqlite` 文件冒充完整备份。备份名带世界文件标识和升级号，禁止覆盖已有成功备份。
3. 关闭/完成备份句柄，检查备份 user_version、integrity_check、foreign_key_check、正式行数和 head，计算 SHA256。备份完成及校验成功之前不写升级事务。
4. 流式扫描全部不可变正式回合，校验单父链/head/count并建立来源索引，再在内存转换旧head状态及混合历史视图；不得复用仅返回最近100回合的GameStore::view。转换器显式接收来源索引并验证v2；所有名称、生命状态、资源单位金额、关系、时间、旧事件和现有知情引用保持对应。缺乏证据的新字段使用 legacy 标记，不能联网补猜。
5. 开启短 IMMEDIATE 事务，再核对同一 head/count/current_state；创建升级记录、更新当前规范化投影、写 user_version=2，一并提交。无网络或模型调用位于事务中。
6. 提交后重开并比较规范化当前视图与旧备份转换结果；备份长期保留，清理策略留 M06，不把失败升级覆盖备份。

空间不足、只读目录、备份/校验失败时保持 v1，明确升级失败并给安全错误。事务提交前进程终止后仍是可用 v1，提交后终止则为完整 v2；备份成功但事务未开始最多留下一个可识别备份。若恢复旧版本，要在应用关闭且没有活操作后从备份创建单独恢复文件并验证，不能覆盖或删除唯一原档来“修复”。旧应用应因 user_version=2 拒绝写入；回退使用 v1 备份，不能用 M02 exe 直接打开升级原档。

### 7.3 v1 字段转换政策

| 旧字段 | 确定性转换 |
| --- | --- |
| id/kind/name/alive、时间、资源、关系 | 原值保持；aliases 初始为空，不虚构别名/年龄或日期 |
| 初始 travel-bag.ownerId=player | 仅可信初始结构及完整历史中未改变持有属性的固定行囊可建立player/1/件，source=initial；若已转交/改归属，按当前旧记录冻结规则转换，不重新归给player |
| 模型创建 item 的持有属性 | 原attributes及原始快照保留；仅ownerId精确指向现有人/组织、quantity为规范非负安全整数十进制、unit非空合法且无冲突别名/地点时，转换为known并带legacy_snapshot来源。缺失单位、冲突或非法值为legacy_unknown，不猜“份”等单位 |
| conditions | 原描述/active/主体保持；类别 legacy_unspecified；由快照序列追溯出现/解决来源，不凭描述猜医疗诊断 |
| events | ID/文本/实体引用保持，disclosure=legacy_unspecified；不得迁移为全世界公开 |
| knownFacts | 映射至 event knowledge，相同 actor/target 保持；certainty/acquisitionMode=legacy_unspecified；不增加任何新知情者 |
| 新 claims | 空列表，不把正文中的每句话或 uncertainties 自动变成客观事实 |

合法转换是原游戏记录的兼容保留，不增加“已考证”的标签；异常记录仍可查看，但确认前不用于消费/转交结算，相关行动明确提示待确认，不能静默当数量0。迁移规则版本冻结，不从名称推单位或从正文补所有权。

旧私有十回合不写入源码。验收对私有备份运行只读比较，永久文档只登记安全摘要；自动测试使用不含秘密和私人剧情的固定 v1 夹具。

## 10. 最小实施顺序与协调点

1. 根代理审查身份/持有物/知识政策，登记一个采纳决策；在任务台账把本任务分成协议、迁移、查询/界面三个验收步骤，整项仍保持进行中。
2. 冻结并保留现行 v1 类型/解析器，先加入 v2 DTO及纯函数；用固定 fixture验证同名、改名、库存原子性、状态持续与知情隔离。只读查询不另建权威表。
3. 为rusqlite接入已验证的backup功能及一致性备份、完整历史扫描、显式SQLite v2迁移，先对无秘密固定v1夹具强杀；再对真实十回合的私有备份运行验证，原档未验收前不升级。
4. UI/native允许混合历史读取，普通页与调试视图区分；更新Provider的v2输出提示及固定Provider。手机验收基线仍独立保留，避免以变化的APK推翻M02证据。
5. 实测v2当前事实体积。M02的8192字节输入上限会因新增字段更早触发；只序列化模型必要的事实视图，来源全文仍在本地可查。T001先实现有界最小事实视图和实际体积测量，原始来源/全文留本地查询。必要事实超限必须在HTTP前明确失败；完整检索/摘要预算仍归T003。T001验收不依赖T003完成，若数据规模要求扩大上限或改变生产启用范围，另记决策并拆分依赖，不能形成T001→T003→T002→T001循环。
6. 通过查询/协议/迁移与旧档兼容门槛后才完成M03-T001；再领取T002检索，不把设计文件当功能成果。

需要根代理采纳的具体选择：

- **推荐**：采用严格v2输出/状态、SQLite v2升级记录及保留v1原始历史的转换器。相比在v1属性里继续编码数组和数量，有明确校验与回退边界；代价是需要同步UI、Provider、迁移与兼容测试。
- **修订建议**：合法旧ownerId/quantity/unit按冻结规则转换并保留legacy来源，异常值为legacy_unknown；可信初始行囊做窄特例。保留原游戏可用记录，避免所有旧物品都被迫重新确认；代价是固定解析规则和合法/异常双轨回归。具体生产采纳仍须根代理登记决策。
- **推荐**：以事件事实+claims+少量活跃角色knowledge满足知识边界；不新增全NPC心智循环或第二个每回合模型调用。当前操作预算和网络授权均保持。
- **修订实施顺序**：T001完成最小事实视图、体积测量及HTTP前超限拒绝，不依赖尚未满足前置的T003；完整预算归T003。若需调整生产切换范围，用独立任务步骤和决策明确依赖。不能让为手机验收冻结的M02 APK读取新schema2原档，也不能把未通过兼容门槛的升级推给用户选择。

以上属于可由源码、固定夹具和工程评审决定的技术选择，不需要让用户重复选择平台、真机、API或模型。
