# R01 格式实验（V101）

> 2026-10-16（Asia/Shanghai）。脚本 `scripts/eval/format-experiment.ts`，原始记录在本机 `.cache/eval/format-2026-10-16T10-20-44/`（不入 Git）。任务 R01-T004，决策 V101。

## 方法

- 模型：用户的第三方中转服务上的 `gemini-3.8-flash-high`（推理模型）。服务地址与 Key 不记录。
- 背景：唐天宝七载长安，主角李安，起始 300 文、欠房钱 90 文。
- 同一组 20 个固定行动，三种格式各自完整跑一遍（各自维护简易状态，后面的回合看得到前面的结果）。其中 12 个行动带自动探针：动作范围、领工钱、买饼并吃掉一个（钱和数量）、半个时辰换算、付房钱、钱不够买马、重复人物、导演指令造成扭伤、只问价不买、睡到天亮、新目标、送出最后一个饼。
- 格式：
  - **A**：正文 + 末尾 `<record>` 标签包裹的紧凑 JSON；
  - **B**：正文 + 末尾“【记录】”逐行文本；
  - **C**：只写正文，另发一次调用从正文提取 JSON。
- 调用：A 20 次、B 20 次、C 40 次，共 80 次，均在事先同意的 90 次上限内；没有失败、没有重试。

### 探针失败的原因（人工阅读原文）

- **三种格式都失败的 #6“老老实实干完今天的活”**：前几回合剧情已经让管事拒绝雇用主角，固定剧本的这一步与剧情冲突，模型照剧情写被赶走，属于剧本问题，不是格式问题。R02 的评测改用会看剧情的“自动玩家”。
- **A #4**：管事把两文钱扔进泥里，记录记了 +2 文，但后文主角并没有捡起这两文（#7 写“那两枚铜钱便留在了身后”）。这是正文与记录不一致的真实案例。
- **B #7**：模型写成“钱：-6文（现余294文）”，逐行格式容易让模型附加说明，我写的解析器因此读错；B #9 正文声称主角“分文皆无”，与上下文给出的余额 294 文矛盾。
- **C #9、#15**：剧情走向与行动不同（被掌柜拒收、被赶出邸店），提取调用如实反映了正文；C 的问题是慢且贵，并会忠实记录正文中的错误。

### 其他观察

- **首字等待约 7 秒**：三种格式差别不大，主要是推理模型先“思考”。这是体验上的最大短板，R02 需要用不带推理的模型做对照（V103）；界面在等待时要显示“构思中…”。
- **人物重复**：A 先记“货栈管事”，后来同一人自报姓名“刘三郎”，被记成两个人。已在状态规则中支持“记录里用 aliases 写出旧称呼”合并为同一人物，并会在提示词 v1 中要求模型这样写（R02-T004、R02-T014）。
- **时代错误**：三种格式的正文共出现 28 次“算盘”（唐代商铺不应出现，应为“算筹”），需要时代包的禁忌清单（R03）和提示词约束。
- 文笔整体可读：有画面、有人物、能遵守“只写到玩家需要决定为止”；有时一回合推进较多情节，篇幅略长于要求的三百字。

## 结论

**选定格式 A（正文 + `<record>` JSON）**，理由：

1. 探针通过率最高，钱数与时间换算最准；
2. 首字延迟与总耗时最低，比 C 每回合快约 7 秒、省约 30% token；
3. JSON 解析比逐行文本更稳，不容易被模型附加的说明打断。

V101 通过标准中“记录成功率 ≥ 95%”“首字延迟不劣于纯正文”在本次样本中满足（A 首字中位 6.8 秒，纯正文的 C 为 7.5 秒）。样本只有一个模型、一个时代、20 回合，换模型后需要用 R02 的评测复查。
